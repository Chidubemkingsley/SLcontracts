# Storage-key design

Soroban's `#[contracttype]` representation supports at most **50 variants per
enum**. The contract therefore splits storage keys across two enums and, for
new composite keys, uses standalone structs as direct storage keys.

## Current budget

| Enum | Variants | Limit | Headroom | Status |
|---|---:|---:|---:|---|
| `DataKey` | 50 | 50 | 0 | **Full — do not add variants** |
| `DataKey2` | 2 | 50 | 48 | Reserved for new singleton keys |

`DataKey::VARIANT_COUNT`, `DataKey::VARIANT_HEADROOM`, and the equivalent
`DataKey2` constants are generated by the `contract_data_key!` macro in
`contracts/sorobanlard/src/lib.rs`. Compile-time assertions fail the build if
either enum exceeds the 50-variant limit, and a unit test asserts the exact
counts documented above.

## Decision rule

### Use a standalone composite key struct (default for new keys)

```rust
#[contracttype]
#[derive(Clone, Debug)]
pub struct ExampleKey {
    pub student: Address,
    pub course_id: String,
    pub attempt: u32,
}

// Store directly; no DataKey variant is added.
env.storage().persistent().get(&ExampleKey {
    student,
    course_id,
    attempt,
});
```

Choose this when **any** of the following is true:

- the key is a composite identity (two or more fields), or is likely to gain
  fields later;
- the key is new — `DataKey` has no headroom;
- named fields make the key easier to read and audit;
- the key is specific to one feature and does not need a shared namespace.

Existing example: `ArbitrationCaseKey { caller, course_id }` in `lib.rs`.
This is the preferred pattern for all new composite keys.

### Use a tuple variant inside `DataKey` / `DataKey2`

```rust
pub enum DataKey {
    Enrollment(Address, String),
    RefundRequest(Address, String),
}
```

Choose this **only** when:

- the key already exists on-chain and changing its encoding would require an
  explicit migration plan; or
- the key is a simple, flat tuple of primitive `contracttype` values and there
  is verified headroom in that enum.

Existing tuple variants such as `Enrollment(Address, String)` and
`RefundRequest(Address, String)` are legacy encodings. Keep them as-is for
compatibility, but **do not add new tuple-style variants**. `DataKey` is full,
and `DataKey2` is reserved for singleton keys so it does not become a second
overflow bucket for composites.

### Singleton keys

Keys with no payload (or a single simple value) go in `DataKey2` while it has
headroom, for example `HighValueCourseThreshold`. Do not introduce a new enum
unless `DataKey2` also approaches its limit; at that point update this document
and the compile-time budget checks as part of the same PR.

## Rules for contributors

1. Never remove, rename, or reorder an existing `DataKey`/`DataKey2` variant
   without a storage-migration plan — the variant index is part of the XDR
   encoding.
2. Never add a composite tuple variant to `DataKey`; it is at 50/50.
3. New composite keys use a standalone `#[contracttype]` struct stored
   directly. Do not add a matching `DataKey` marker variant.
4. New singleton keys use `DataKey2` until its headroom is exhausted.
5. If an enum's variant count changes, update the comments at the top of the
   enum, this document, and the exact-count test in `src/test.rs`.
6. Do not mix styles for the same logical key. Pick one representation and use
   it for every read and write.

## Why not always use structs?

Tuple variants are already deployed in existing contract storage. Rewriting
their keys would orphan existing data unless a migration function rewrites every
record. New code uses structs because they provide explicit field names, are not
subject to the enum variant budget, and keep unrelated feature keys out of a
single global enum.
